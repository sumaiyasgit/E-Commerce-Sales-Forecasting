## Project Overview

E-commerce businesses generate large amounts of transaction data.
Understanding historical sales and estimating future demand can support
inventory planning, marketing decisions, staffing, and business operations.

This project prepares transaction-level data, aggregates revenue by date,
analyzes temporal patterns, engineers forecasting features, and trains
machine-learning regressors to predict daily revenue.

## Problem Statement and Objectives

Businesses need estimates of future sales to make informed operational
decisions. Raw transaction records must be cleaned, aggregated, and
transformed into forecasting-ready data.

**Main objective:** Analyze historical e-commerce sales and develop a
machine-learning model that predicts daily revenue.

Project objectives:

- Inspect and prepare transaction-level sales data.
- Explore sales patterns by date and available business dimensions.
- Aggregate transaction revenue into a daily time series.
- Engineer lag, rolling-average, and calendar features.
- Train and compare a naive baseline and machine-learning models.
- Tune model hyperparameters with time-series cross-validation.
- Evaluate predictions using MAE, RMSE, and MAPE.
- Save the final model and feature configuration for application integration.
- Forecast future revenue and serve it through a web application.

## Machine-Learning Methodology

### 1. Daily aggregation

Transaction revenue is summed by `order_date` to create the `daily_revenue`
target.

### 2. Feature engineering

The model uses 12 input features.

**Calendar features**

| Feature | Meaning |
|---|---|
| `day_of_week` | Day of week, Monday = 0 through Sunday = 6 |
| `day_of_month` | Day number within the month |
| `month` | Month number |
| `quarter` | Calendar quarter |
| `year` | Calendar year |
| `is_weekend` | 1 for Saturday/Sunday, otherwise 0 |

**Lag features**

| Feature | Meaning |
|---|---|
| `lag_1` | Revenue one day earlier |
| `lag_7` | Revenue seven days earlier |
| `lag_14` | Revenue fourteen days earlier |
| `lag_30` | Revenue thirty days earlier |

**Rolling features**

| Feature | Meaning |
|---|---|
| `rolling_mean_7` | Mean revenue over the previous seven days |
| `rolling_mean_30` | Mean revenue over the previous thirty days |

Rolling features use a one-day shift before calculating the rolling window,
so the current day's target is not included in its own inputs.

The first 30 rows are dropped because 30 days of history are required. From
730 daily observations, 700 feature-ready rows remain.

### 3. Chronological train/test split

The 700 feature-ready rows are split in date order:

- Training: first 80%, or 560 rows (31 Jan 2022 to 13 Aug 2023).
- Testing: final 20%, or 140 rows (14 Aug 2023 to 31 Dec 2023).

The observations are not randomly shuffled. This preserves the forecasting
direction: train on earlier observations and evaluate on later observations.

### 4. Models

The following models were evaluated:

- Naive baseline: predicts the next day's revenue as the previous day's
  actual revenue.
- Linear Regression
- Random Forest Regressor
- Gradient Boosting Regressor

### 5. Hyperparameter tuning

Random Forest and Gradient Boosting were tuned using `GridSearchCV` and
`TimeSeriesSplit` with negative MAE as the scoring metric.

Best Random Forest parameters:

```python
{
    "n_estimators": 200,
    "max_depth": 10,
    "min_samples_leaf": 3
}
```

Best Gradient Boosting parameters:

```python
{
    "n_estimators": 100,
    "learning_rate": 0.03,
    "max_depth": 2
}
```

The held-out test set was not used for hyperparameter selection.

|---|---:|---:|---:|
| Random Forest | **5,786.01** | 7,290.58 | 13.44% |
| Gradient Boosting | 5,799.69 | **7,255.80** | **13.42%** |

### Selected model

Random Forest was selected as the final model because it achieved the lowest
test MAE, the primary selection metric used in this project. The difference
from Gradient Boosting is small: Gradient Boosting achieved slightly lower
RMSE and MAPE. The selection therefore reflects the chosen primary metric,
not universal superiority.

**Final Random Forest test results:**

| Metric | Result |
|---|---:|
| MAE | 5,786.01 |
| RMSE | 7,290.58 |
| MAPE | 13.44% |

Metric definitions:

- **MAE:** Average absolute difference between actual and predicted revenue.
  Lower is better.
- **RMSE:** Square root of mean squared prediction error; larger errors
  receive more weight. Lower is better.
- **MAPE:** Average absolute percentage error for nonzero actual values.
  Lower is better.

These are revenue-unit errors. The dataset does not state a currency.

## Residual Analysis

Residuals are calculated as:

```text
Residual = Actual Revenue - Predicted Revenue
```

A positive residual means underprediction; a negative residual means
overprediction.

| Statistic | Value |
|---|---:|
| Count | 140 |
| Mean | -295.24 |
| Standard deviation | 7,310.76 |
| Minimum | -15,596.71 |
| Median | -761.61 |
| Maximum | 20,802.83 |

Several of the largest errors occurred on dates when actual revenue was above
approximately 58,000 while the model predicted around 42,000-45,000. This
suggests difficulty capturing some high-sales days. These observations should
be investigated rather than removed automatically.

## Forecasting, Evaluation and Deployment (Person 4)

### Fair evaluation

Accuracy was measured with `random_forest_tuned.joblib`, which was trained
only on the first 560 days and never saw the test months. `final_model.joblib`
was re-trained on all 700 days, so it is used only for the future forecast.
Testing it on the test months would be misleading, because it has already seen
those days.

Results on the 140 unseen test days, one day ahead:

| Method | MAE | RMSE | MAPE | R² |
|---|---:|---:|---:|---:|
| Yesterday's revenue | 8,530 | 10,459 | 19.5% | -1.07 |
| Same weekday last week | 8,554 | 10,653 | 19.8% | -1.15 |
| Average of last 30 days | 5,970 | 7,455 | 13.9% | -0.05 |
| Training-period average | 5,815 | 7,283 | 13.6% | -0.01 |
| **Random Forest** | **5,786** | **7,291** | **13.4%** | **-0.01** |

**Finding:** the model beats the naive baselines by about 32% in MAE but only
ties the plain average (R² is about 0). Daily revenue in this dataset behaves
almost randomly: its correlation with the previous day is about -0.06 and
average revenue varies little by weekday. When data has almost no pattern, no
model can do much better than the average. This is reported openly rather than
hidden.

### Multi-day forecast

Future days are forecast **recursively**: predict one day, add the prediction
to the history, recompute the lag and rolling features, and repeat. A
back-test from every test date shows the 7-, 30- and 90-day forecasts have
about the same average error as repeating the recent average
(MAE about 5,800 to 6,100).

Forecast for 1 Jan to 30 Mar 2024, with likely ranges (about 80% of past
outcomes, approximate):

| Period | Expected total revenue | Likely range |
|---|---:|---|
| Next 7 days | 328,463 | 302,351 to 354,575 |
| Next 30 days | 1,392,596 | 1,339,118 to 1,446,074 |
| Next 90 days | 4,085,456 | 3,994,877 to 4,176,035 |

A single day can differ from its forecast by about -22% to +21%, but totals
over many days are far more certain because daily errors cancel out.

### Web application

The Flask application in `app/` lets a user choose a 7-, 30- or 90-day period
and shows the expected revenue, a likely range, a past-and-forecast chart, a
weekly breakdown and an accuracy panel. It reads precomputed forecast files
instead of loading the model, so it responds instantly and avoids
library-version problems on the server. It is deployed on Render:
<(https://sales-forecaster-o5i2.onrender.com)>

Charts and metric tables are in `reports/figures/`. The scripts and a
step-by-step guide are in `forecasting/`.

## Forecasting Considerations

### One-day-ahead and multi-day forecasts

The reported test evaluation is a rolling one-day-ahead setup: each test-day
prediction uses the previous day's actual revenue as an input. This assumes
that the previous day's actual sales are available at prediction time.

For a future 7-, 30-, or 90-day forecast, actual future sales are not
available. The application therefore uses recursive forecasting (implemented in
`forecasting/forecast_utils.py`):

1. Calculate features from available historical observations.
2. Predict the next day.
3. Append that prediction to the history used to calculate subsequent lag and
   rolling features.
4. Repeat for the requested horizon.

Actual future target values are never used to create later forecast features.
Multi-day performance was tested separately with a rolling-origin back-test
(see the Person 4 section).

### Model retraining

The final saved Random Forest was retrained on all 700 feature-ready rows
after test evaluation. The reported test metrics belong to the model trained
on the first 560 rows and evaluated on the final 140 rows. Do not report the
all-data model's training performance as test performance.

### Feature consistency

The application must use the same feature definitions, names, ordering, and
compatible preprocessing as model training. `feature_columns.joblib` records
the expected feature order.

## Limitations and Future Improvements

- The dataset appears to contain very little weekly or seasonal pattern, so
  the model cannot clearly beat a plain average.
- Recursive multi-day forecasts can accumulate error, and the likely ranges
  are approximate.
- The website forecasts total revenue only; there are no category-level
  forecasts.
- Investigate high-error dates and possible promotions or sales events.
- Add holiday or promotion indicators if reliable data is available.
- Compare additional forecasting approaches such as ARIMA or Prophet.
- Monitor forecast errors as new data arrives and re-train when needed.
- Validate on a newer, genuinely unseen period, ideally with real data.
